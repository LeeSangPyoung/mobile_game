# 손가락삼국지 · 실시간 1v1 멀티플레이 설계 문서 (v0.2)

갱신: 2026-07 / 모델 **실시간 1v1 대칭 영토전** / 아키텍처 **P2P 호스트 권위 + Firebase(경량 백엔드)**

> 코드 근거로 "무엇을/순서/리스크"를 못박는 설계서. 코드는 이 문서 합의 후 착수.
> **확정된 결정**은 §1·§2·§8에 반영됨. 미결정은 §11.

---

## 1. 목표와 범위 (확정 반영)

- **모드**: 실시간 1대1. 두 사람이 같은 대칭 맵에서 동시 성 점령·공방.
- **편성**: 보유 로스터에서 **장수 10명**(현행 유지). 밴픽 없음.
- **승리 조건**: **상대 본진 함락 = 즉시 승. 제한시간 없음.** (시간승/무승부 규칙 없음)
- **계정**: **게스트 자동부여**(회원가입 없음). **닉네임만** 첫 로딩 때, 없을 때만 입력.
- **비목표(1차 제외)**: 2v2/협동, 관전, 리플레이, 시즌 랭킹.
- **1판 길이 목표**: 3~7분.

---

## 2. 대전 형식 — 대칭 영토전

- **맵**: 점대칭. 양 끝 본진 1개씩, 사이에 중립성 다수. 완전 대칭이라 위치 유불리 없음.
  - 기존 `genStageLayout`/`makeGeneratedStage`를 **대칭 PvP 생성기**로 개조.
- **시작**: 양쪽 본진 동일 병력 + 각자 10장 편성 입장.
- **승패**: 본진 함락 즉시 종료. 항복 = 패. 호스트 이탈 처리는 §7.

## 3. 현재 코드 구조 진단 (근거)

| 요소 | 위치 | 성격 |
|---|---|---|
| 성 상태 | `let castles=[]` (prototype.html:17744) | 전역 가변 |
| 부대 상태 | `const armies=[]` (17816) | 전역 가변 |
| 시뮬 스텝 | `update(dt)` (19896) | **가변 dt**, 30fps, 렌더/UI와 강결합 |
| 핵심 명령 | `sendArmy(...)` (19143) | 유일 플레이어 입력 |
| 전투 | update 내부: 부대-부대(19526), 부대-성(19658/19817) | |
| 렌더 | `render(dt)` (24768), `loop(t)` (25513) | |
| 난수 | `Math.random` 307곳 | 시뮬+연출 혼재 |

**강결합 실측(update 본문)**: `document.body.classList`, `window._legendTick`, `updateFactionLegend()`, `msgShown`, `camX/Y/zoom`, `clampCamera()`, `updateCinematic()`, `showSpeech()` 등 UI/렌더 직접 호출.

**⚠ 치명적 발견 — 시뮬 좌표가 뷰포트 종속**
- 부대 위치 `army.x/y`가 **픽셀값**, 성 좌표는 `k.x * worldPxW()`로 픽셀 변환해 사용.
- 감지반경이 `AGGRO_DIST() / zoom` → **카메라 줌이 시뮬(aggro) 결과를 바꿈**, `DPR()`도 개입.
- 즉 시뮬이 화면 픽셀/DPR/줌에 얽혀 있어, **다른 기기(호스트)에서 같은 결과를 보장 못 함.**
- → Phase 0에 **좌표계를 월드단위(뷰포트 독립)로 전환**이 반드시 포함.

## 4. 넷코드 아키텍처 — P2P 호스트 권위

```
[폰A 호스트: engine.js 권위 시뮬]  <== WebRTC DataChannel ==>  [폰B 게스트: 명령 송신 + 렌더]
      │  직접연결 실패 시만 ↓ TURN 릴레이                          │
      └──────────── 결과 보고 ─────►  [Firebase]  ◄──── 결과 보고 ──┘
                          (익명계정 · 닉네임 · 전적 · 시그널링)
```

- **호스트 폰이 진짜 시뮬**을 돌린다(engine.js). 게스트는 명령만 보내고 호스트가 준 상태를 **그려주기만**.
- **틱**: 고정 15Hz(dt=1/15). 호스트가 상태 스냅샷을 10~15Hz로 게스트에 전송.
- **왜 P2P 호스트인가**: 상시 게임서버 불필요 → 서버 부담·비용 최소. 느린 명령형 RTS라 P2P 지연에 관대.

### 연결 수립 흐름
1. 두 클라가 Firebase 매칭 큐에서 페어링 → 한 명이 **호스트** 지정(예: 먼저 들어온 쪽).
2. **시그널링**: SDP/ICE를 Firebase Realtime DB로 교환(매치당 메시지 몇 개, 상시부담 X).
3. **STUN**(무료 공용)으로 NAT 관통 시도 → 실패 시 **TURN 릴레이** 폴백.
4. DataChannel 연결 → 매치 시작.

### 명령 프로토콜 (MVP)
```
Guest→Host  SEND_ARMY  { fromId, toId, unit, ratio|withCommander, commanderUid? }
Guest→Host  SURRENDER  {}
Host→Guest  STATE      { tick, castles[], armies[] }          // 스냅샷(diff 가능)
Host→Guest  MATCH_START{ seed, mapDef, youSide, oppRoster }
Host→Guest  MATCH_END  { winner, reason }
양쪽→Firebase  RESULT   { matchId, reporterUid, winner, tick }  // 각자 보고(불일치 플래그)
```
- 호스트는 게스트 명령을 **자기 틱에서 검증 후 적용**(소유권·병력·쿨다운). 부정 명령 무시.

## 5. 결정론화 — 부담 최소 판단

- 호스트가 유일 권위이므로 **게스트는 결정론 불필요**(호스트 상태를 그리기만).
- **MVP는 게스트 예측 없이 보간만** → 클라 결정론 부담 제거(느린 RTS라 100~150ms 보간 OK).
- **호스트 시뮬만** 재현가능하면 됨:
  1. **고정 timestep**(가변→1/15).
  2. **좌표계 월드단위 전환**(§3 발견) — 픽셀/DPR/zoom 의존 제거.
  3. 시뮬용 `Math.random` → 매치 seed `rng()`. 307곳 중 **시뮬 영향분만** 교체(연출/파티클은 그대로).

## 7. 클라 예측·보간·이탈

- **보간(MVP)**: 스냅샷 2개 시간보간으로 부드럽게. 입력 즉시엔 로컬 "출발 고스트" 표시 후 호스트 확정으로 대체.
- **호스트 이탈**: 권위가 호스트에 있어 이탈 시 매치 지속 불가 → **게스트 승 처리**(또는 무효), Firebase 기록.
- **게스트 이탈**: 30초 유예 후 호스트 승.
- (후순위) 호스트 마이그레이션/권위서버 승급은 랭크 도입 시.

## 8. 백엔드 인프라 = Firebase (확정 방향)

| 구성 | 선택 | 매핑 |
|---|---|---|
| 게스트 계정 | **Firebase 익명 인증** | UID 자동부여, 회원가입 없음 |
| 닉네임/전적 | **Firestore** | 첫 로딩 시 닉네임 없으면만 입력→저장 |
| 매칭/시그널링 | **Firebase Realtime DB** | 큐 + SDP/ICE 교환 |
| P2P | **WebRTC DataChannel** | 호스트↔게스트 직접 |
| NAT 폴백 | **TURN**(Metered/Twilio 관리형 or coturn VPS) | 직접연결 실패 시만 과금 |

- **상시 게임서버 0.** 무료 티어로 시작 가능. **유일한 소액 상시비용 = TURN 폴백 대역폭.**
- **닉네임 흐름**: 부팅 시 `auth.currentUser`(없으면 익명 로그인) → Firestore `users/{uid}.nick` 조회 → 없으면 1회 입력 모달 → 저장. 있으면 스킵.

## 9. 치팅 방어 (캐주얼 MVP 수용)

- **호스트가 자기 시뮬을 조작 가능** = P2P 호스트의 본질적 약점. **캐주얼/친선 MVP에선 수용**.
- 완화: 양쪽이 결과를 각자 Firebase 보고 → **불일치 시 플래그**(무효/재검). 비정상 명령 빈도 레이트리밋. 로스터는 입장 시 실제 보유분과 대조.
- **정식 랭크 도입 시** 권위 전용 서버로 승급(엔진이 이미 분리돼 있으므로 재사용).

## 10. 단계별 로드맵

| Phase | 내용 | 완료 기준 |
|---|---|---|
| **0. 엔진 분리 + 좌표계 전환** | engine.js 추출, 월드단위 좌표, 고정 dt, 시드 rng | 싱글 리그레션 0 |
| **1. 백엔드 골격** | Firebase 익명인증 + 닉네임 + 매칭/시그널링 | 두 클라 페어링→시그널 교환 |
| **2. P2P 대전** | WebRTC 연결, 호스트 권위 시뮬, 게스트 명령/보간, TURN 폴백 | 2인 실전 1판 완주(본진함락 승) |
| **3. 대전 완성도** | 대칭 맵 생성기, 10장 편성 화면, 승패/전적, 항복·이탈 | 캐주얼 매치 배포 가능 |
| **4. 운영·강화** | 레이팅/랭킹, 치팅 하드닝, (필요시) 권위서버 승급 | 정식 시즌 |

## 11. 미결정 사항

1. **자원/생산 규칙**: 싱글과 동일? PvP 전용 밸런스?
2. **매칭 범위**: 친선전(방 코드 초대)만 먼저? 랜덤 매칭까지 한 번에?
3. **호스트 지정 규칙**: 먼저 입장/네트워크 좋은 쪽/랜덤?
4. **TURN 제공**: 관리형(Metered 등) vs 자체 coturn.
5. **대칭 맵 규모**: 성 몇 개? (블리츠 후반은 PvE용; PvP는 별도 중간 규모 권장)

## 12. 리스크 & 견적 (솔직)

- **최대 리스크 = Phase 0**, 특히 **좌표계 뷰포트-종속 해소**. 단순 파일 분리가 아니라 시뮬 좌표 리팩터라 공수가 큼. 싱글 리그레션 위험 관리 필수.
- **P2P 현실**: 모바일 NAT로 직접연결 실패율이 있어 TURN 의존이 생김(소액 상시비용).
- **치팅**: 캐주얼은 수용, 랭크는 권위서버 승급 전제.
- **개략 공수**: Phase 0(가장 큼) → 1 → 2가 각각 유의미한 덩어리. "몇 주~몇 달", 단계별 산출물로 쪼개 진행.
