# 세이브 동기화 설계 — 유저는 아무것도 하지 않는다

작성 2026-08-31 · 대상 `com.leesp.samgukgi` 1.0.27(28) 이후

> **개정 이력**
> - 1판: 구글 로그인 버튼을 유저가 직접 누르는 방식으로 설계했다.
>   "설정에 넣어두면 평생 모른다" 는 지적이 맞았다. 요즘 안드로이드 게임은
>   그렇게 하지 않는다.
> - **2판(현재): 구글 플레이 게임즈 자동 로그인.** 유저 동작 0.

---

## 1. 왜 필요한가

유저 이탈이 실제로 나왔다.

- A폰에서 하다 B폰에서 받으니 **처음부터** → 그만둠
- A폰에서 지웠다 다시 까니 **처음부터**

버그가 아니다. 지금 구조가 그렇다.

```js
function saveProgress() { localStorage.setItem('save', JSON.stringify(SAVE)); }
```

세이브는 **그 폰의 그 앱 안에만** 있다. 서버로 가는 건 설치 집계 비콘(`cid`)과
멀티 대전 전적뿐이고, 진행도는 한 바이트도 안 올라간다.

`AndroidManifest.xml` 에 `allowBackup="true"` 가 있어 안드로이드 자동 백업이
걸려는 있지만, 이건 **새 기기 최초 설정 때 Play 를 거쳐야** 복원된다. 그냥
지웠다 다시 까는 경로는 덮어 주지 못한다.

말하지 않은 위험이 하나 더 있다. 저장 공간이 부족하면 안드로이드는 WebView
데이터를 정리 대상으로 본다. **아무것도 안 했는데** 어느 날 초기화될 수 있다.

## 2. 신원 — 구글 플레이 게임즈 (자동)

세이브를 서버에 두려면 "누구 것인지" 를 알아야 한다. 그런데 그 열쇠를
`localStorage` 에 두면 앱을 지울 때 같이 사라진다. **앱 밖에 남는 신원**이 필요하다.

안드로이드에는 이미 답이 있다. **구글 플레이 게임즈(PGS)** 다.

```
앱 실행
  → PGS 가 폰의 구글 계정으로 자동 로그인   (유저 동작 없음, 화면 없음)
  → 서버에 넘길 인증 코드를 받는다
  → 서버가 구글에 확인하고 그 사람의 uid 를 돌려준다
  → 세이브가 오간다
```

**팝업 없다. 버튼 없다. 설정 항목도 굳이 안 봐도 된다.**
폰을 바꿔도 같은 구글 계정이면 같은 사람으로 인식된다.

### 왜 이게 표준인가

요즘 안드로이드 게임 대부분이 이 방식이다. 유저는 로그인했다는 사실조차
모르고, 폰을 바꾸면 그냥 이어진다. **1판 설계의 「계정 연결」 버튼·팝업·
메인화면 경고는 전부 필요 없어진다.**

### 안 되는 경우와 대비

| 상황 | 처리 |
|---|---|
| PGS 를 꺼 둔 유저 | 익명 계정으로 진행. 설정에서 수동 연결 가능 |
| 구글 서비스 없는 기기 | 위와 같음 |
| 웹(`app.wooriban.org`) | PGS 불가 → 구글 로그인 버튼(수동) |
| 그래도 싫은 사람 | **복구 코드** (설정) |

**소수를 위한 뒷문은 남기되, 앞문은 자동이다.**

### 유저에게 한 번은 알린다 — 알림과 요청을 나눈다

자동으로 다 되니 아무 말도 안 하면 될 것 같지만, 그러면 **유저가 모른다.**
모르면 폰을 바꿀 때 "어차피 날아갔겠지" 하고 앱을 안 깐다. 그만둔 그 유저도
알았다면 달랐을 수 있다.

그렇다고 "계정을 연결하시겠습니까?" 를 띄우면 안 된다. **이미 연결돼 있다.**
물어볼 것이 없는데 물으면 유저가 헷갈린다.

그래서 **성격을 나눈다.**

#### 자동 로그인 성공 → 「알림」 (평생 1회)

```
   ┌────────────────────────────────┐
   │   기록이 안전하게 보관됩니다    │
   │                                │
   │   구글 계정에 연결되어 있어     │
   │   폰을 바꾸거나 앱을 지워도     │
   │   그대로 이어서 할 수 있습니다. │
   │                                │
   │           [ 확인 ]              │
   └────────────────────────────────┘
```

버튼 하나. 「다시 보지 않기」는 **넣지 않는다** — 어차피 평생 한 번이다.
선택지를 주면 오히려 "뭘 고르라는 거지" 가 된다.

#### 자동 로그인 실패 → 「요청」 (소수)

여기서는 실제로 유저가 눌러야 할 것이 있다.

```
   ┌────────────────────────────────┐
   │   ⚠ 기록이 이 폰에만 있습니다   │
   │                                │
   │   폰을 바꾸거나 앱을 지우면     │
   │   처음부터 시작하게 됩니다.     │
   │                                │
   │   [ 구글 계정으로 연결 ]        │
   │   [ 나중에 ]  [ 다시 보지 않기 ] │
   └────────────────────────────────┘
```

「나중에」는 다음 기회에 또, 「다시 보지 않기」는 끝. 연결에 성공하면
그 뒤로 안 뜬다.

#### 언제 띄우나

| 대상 | 시점 |
|---|---|
| 신규 | **1챕터(20장) 클리어 후** — 잃을 게 생긴 다음이라야 와 닿는다 |
| 기존 | **업데이트 후 첫 실행**, 메인 화면으로 돌아왔을 때 |

기존 유저는 1챕터를 다시 깰 일이 없다. 조건을 "1챕터 클리어" 로만 잡으면
**가장 잃을 게 많은 사람들에게 영영 안 뜬다.** 따로 잡아 준다.

둘 다 **스테이지 도중에는 띄우지 않는다.**

#### 「봤음」 표시는 세이브 안에 둔다

```js
SAVE.cloudNoticeSeen = 1;    // localStorage 에 따로 두면 안 된다
SAVE.cloudNoticeMuted = 1;   // '다시 보지 않기'
```

`localStorage` 에 따로 두면 **폰을 바꿨을 때 또 뜬다.** `SAVE` 안에 넣으면
같이 동기화돼 새 폰에서도 안 뜬다. 안내를 한 번만 보여 주려는 것이므로
이 표시도 사람을 따라다녀야 한다.

### 세이브는 우리 서버에 둔다

PGS 에는 저장 기능(Saved Games)도 있다. 구글 드라이브에 알아서 저장해 주고
서버 코드가 필요 없다. 그런데 안 쓴다. 이유는 셋이다.

1. **웹 버전이 못 쓴다.** `app.wooriban.org` 로도 접속한다
2. **문의에 답할 수 없다.** 기록이 구글 드라이브 안에 있으면 우리가 못 본다.
   "기록이 날아갔어요" 에 해 줄 게 없는 건 지금과 똑같다
3. **이미 서버가 있다.** 멀티 계정·전적·이벤트가 전부 거기 있다.
   세이브만 딴 데 두면 나중에 반드시 어긋난다

> **PGS 는 신원 확인에만 쓰고, 저장은 우리 서버가 한다.**

## 3. 데이터

### 얼마나 큰가 — 잰 값

시험 빌드(장수 49명, 전 스테이지 해금) 기준:

```
세이브 전체   2,874 바이트
  generals      2,148   (장수 1명당 약 44바이트)
  audioSettings    73
  upgrades         66
  dailyStar        62
  나머지          전부 100바이트 미만
```

장수 500명을 모은 만렙 유저라도 **30KB 를 넘기 어렵다.**

> 크기가 이 정도면 부분 동기화·델타는 과설계다. **통째로 올리고 통째로 내린다.**

### 유저 정보가 어디에 흩어져 있나 — 전수 조사

동기화에서 가장 흔한 사고는 **일부를 빠뜨리는 것**이다. 장수는 왔는데 강화가
안 왔다든가, 일기토 기록만 사라진다든가. 그래서 저장소를 전부 뒤졌다.

`localStorage` 를 쓰는 키는 여섯 개뿐이다.

| 키 | 내용 | 처리 |
|---|---|---|
| **`save`** | **게임 진행도 전부** | **이것만 통째로 올린다** |
| `liveEvtDone_*` | 깜짝 이벤트 참여 이력 | 서버 `event_completions` 로 일원화 |
| `mp_uid` | 멀티 계정 id | 계정 체계에 흡수 |
| `cid` | 설치 집계용 기기 id | **기기마다 달라야 한다. 옮기지 않는다** |
| `devCheats` | 개발 치트 스위치 | 옮기지 않는다 |
| `__testBuildDone` | 시험 빌드 표식 | 옮기지 않는다 |

`sessionStorage` · `IndexedDB` 는 **0건**. `duel_v2.html` 은 저장을 아예 하지
않는다(일기토 최고 콤보도 `SAVE.duelBestCombo` 로 `save` 안에 있다).

> 유저 게임 정보는 **`save` 하나에 전부 모여 있다.**

### `save` 안에는 뭐가 있나 (실측, 항목 25개)

| 항목 | 내용 | 크기 |
|---|---|---|
| `generals` | 장수 목록 — **강화 레벨·등급이 여기 다 있다** | 2,148B |
| `upgrades` | 전투력 강화 5종 | 66B |
| `stars` | 스테이지별 별 등급(깬 판만 기록) | 판에 비례 |
| `unlocked` / `gold` / `starsAvailable` | 해금 진도 · 골드 · 보유 별 | 각 10B 미만 |
| `formations` / `lastDeployGenerals` / `activeFormation` | 편성 · 최근 출전 | 47B |
| `dailyStar` / `audioSettings` | 오늘의 별 · 소리 설정 | 135B |
| `duelBestCombo` | 일기토 최고 연타 기록 | 수B |
| 나머지 12개 | `tutorialDone`, `generalsV2` 등 마이그레이션 플래그 | 각 4B |

장수 하나가 `{"uid":8,"id":"han_zhong","lv":1,"stars":1}` — **44바이트**다.

### 빠뜨리지 않기 위한 두 가지 규칙

**규칙 1 — 항목을 나열하지 않는다.**

```js
// 이렇게 하면 안 된다. 나중에 SAVE 에 항목이 늘면 조용히 빠진다.
{ gold: SAVE.gold, generals: SAVE.generals, /* ... */ }

// 이렇게 한다. 통째로.
localStorage.getItem('save')
```

**규칙 2 — 올릴 때마다 요약을 함께 남긴다.**

```
rev 7 · 2,874B · 항목 25 · 장수 49 · 별 210 · 골드 12,400
```

항목 수나 장수 수가 갑자기 줄면 **그 자리에서 보인다.** 급감이 잡히면 올리기를
막지는 않되(막으면 정상 유저가 갇힌다) 기록을 남긴다.

### 스키마 (서버, `node:sqlite` — 의존성 추가 없음)

```sql
CREATE TABLE IF NOT EXISTS accounts(
  uid        TEXT PRIMARY KEY,   -- users.uid 와 같은 값을 쓴다(신원 하나로 통일)
  token_hash TEXT NOT NULL,      -- 토큰 원문은 저장하지 않는다. sha256 만.
  pgs_id     TEXT UNIQUE,        -- 플레이 게임즈 플레이어 id  ← 주 신원
  google_sub TEXT UNIQUE,        -- 웹·수동 연결용 구글 계정 id
  created    INTEGER,
  last_seen  INTEGER
);

CREATE TABLE IF NOT EXISTS saves(
  uid      TEXT PRIMARY KEY,
  rev      INTEGER NOT NULL,     -- 올릴 때마다 +1. 충돌 판정의 기준
  data     TEXT NOT NULL,        -- SAVE 를 JSON 문자열로
  size     INTEGER,
  updated  INTEGER,
  cid      TEXT,                 -- 마지막으로 올린 기기
  device   TEXT,                 -- "SM-F926N" 같은 표시용 이름
  summary  TEXT                  -- 규칙 2. 급감 감지용
);

CREATE TABLE IF NOT EXISTS save_history(  -- 되돌리기용. uid 당 최근 5개
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  uid TEXT, rev INTEGER, data TEXT, updated INTEGER
);
```

`users.uid` 를 그대로 쓴다. 멀티 계정과 세이브 계정이 따로 놀면 어긋난다.

## 4. API

기존 서버(`server/mp_server.js`)는 의존성 0, `http.createServer` 에
`if (p === '/beacon')` 식으로 라우트를 붙이는 구조다. 그대로 따른다.

| 메서드 | 경로 | 몸통 | 응답 |
|---|---|---|---|
| POST | `/auth/pgs` | `{ serverAuthCode, cid, device }` | `{ uid, token, rev }` ← **주 경로** |
| POST | `/auth/anon` | `{ cid, device }` | `{ uid, token }` (PGS 없을 때) |
| POST | `/auth/google` | `{ idToken }` | `{ uid, token, rev }` (웹·수동) |
| POST | `/save/put` | `{ uid, token, rev, data, summary }` | `{ ok, rev }` / `409` |
| GET | `/save/get` | `?uid=&token=` | `{ rev, data, updated, device }` |
| POST | `/save/code` | `{ uid, token }` | `{ code }` (복구 코드) |
| POST | `/save/redeem` | `{ code }` | `{ uid, token, rev }` |

### PGS 확인 흐름

```
앱          PGS 로 자동 로그인 → requestServerSideAccess(웹클라이언트ID)
            → serverAuthCode 획득
   ↓
서버        구글에 코드를 토큰으로 교환
            → Games API 로 playerId 조회
            → accounts.pgs_id 로 찾거나 새로 만든다
            → { uid, token } 발급
```

구글 확인은 HTTPS 요청 두 번이다. **`node:https` 만으로 된다** — 의존성 0 원칙 유지.

## 5. 언제 올리고, 언제 내리나

### 올리기 (put)

- 스테이지 클리어
- 장수 등용 / 강화 / 전투력 강화 (돈이 오간 순간)
- 앱이 백그라운드로 갈 때 (**가장 중요하다**)
- 위를 10초 창으로 묶어 한 번만

실패해도 게임은 그냥 흘러간다. **동기화 때문에 게임이 멈추는 일은 없어야 한다.**

### 내리기 (get)

앱을 열 때 한 번. 서버 `rev` 와 로컬 `rev` 를 비교한다.

```
서버 rev  ==  로컬 rev   → 같다. 그냥 시작
서버 rev  <   로컬 rev   → 내가 최신. 올린다
서버 rev  >   로컬 rev   → 서버가 최신. 내려받는다
서버·로컬이 갈라짐        → 유저에게 묻는다 (아래)
```

### 갈라졌을 때 — 자동으로 고르지 않는다

A폰에서 12장, B폰에서 3장이면 어느 쪽도 "틀린" 게 아니다.
**말없이 하나를 죽이면 그게 제일 큰 사고다.**

```
   이어서 할 기록을 고르세요

   ┌─ 이 기기 ──────────────┐   ┌─ 다른 기기 ────────────┐
   │  3장 5절                │   │  12장 20절              │
   │  장수 11명 · 별 40      │   │  장수 34명 · 별 210     │
   │  오늘 14:02             │   │  어제 21:30             │
   │      [ 이걸로 ]         │   │      [ 이걸로 ]         │
   └────────────────────────┘   └────────────────────────┘

   고른 쪽으로 시작합니다. 다른 기록도 7일간 보관됩니다.
```

**유저가 이 화면을 볼 일은 거의 없다.** 두 기기를 오프라인으로 번갈아 써야
나온다. 그래도 있어야 한다 — 없으면 그때 조용히 한쪽이 죽는다.

## 6. 보안 — 지금 있는 구멍부터

현재 멀티 로그인에는 비밀이 없다.

```js
if (m.uid) { const u = db.prepare('SELECT * FROM users WHERE uid=?').get(m.uid);
             if (u) { ... ws.uid = u.uid; ... } }   // uid 만 맞으면 그 사람이 된다
```

uid 를 알아내면 **남의 계정이 된다.** 지금은 전적만 걸려 피해가 작지만,
세이브를 얹으면 **남의 진행도를 읽고 덮어쓸 수 있게 된다.**

→ `accounts.token_hash` 를 만들면서 **멀티 `hello` 도 토큰을 요구하도록 함께
고친다.** 기존 유저는 첫 접속 때 토큰을 발급해 주고 넘어간다(1회 유예).

그 밖에:

- 토큰은 32바이트 난수, 서버엔 **sha256 만** 저장
- `data` 상한 256KB. 넘으면 거절
- `/save/put` 은 uid 당 분당 6회 제한
- 복구 코드는 **1회용**
- HTTPS 만

### 치팅

세이브는 클라이언트가 만든다. 고쳐 올리면 서버는 모른다. **이 설계로는 못
막는다.** 다만 싱글 진행도는 남에게 피해가 없고, 멀티는 전투력 매칭이라
부풀리면 자기가 센 상대를 만난다. 서버에 상식 검사만 붙여 기록을 남긴다.

---

## 7. 순서

### 1단계 — 바닥 (0.5일)

- 서버: `accounts` / `saves`, `/auth/anon` `/save/put` `/save/get`
- 클라: 익명 계정, 올리기·내리기, `rev` 관리
- 멀티 `hello` 토큰 도입 (6항의 구멍 메우기)

→ 유저 눈에 변화 없음. 그날부터 **모든 기록이 서버에 백업**된다.
   문의가 오면 찾아 줄 수 있게 된다.

### 2단계 — 재설치 (0.5일)

- 토큰을 네이티브 저장소(Capacitor Preferences)에 복제
- 시작 시 localStorage 에 토큰이 없으면 네이티브에서 찾는다

→ **"지웠다 깔았더니 처음부터"** 가 풀린다. 유저 동작 없음.

### 3단계 — 플레이 게임즈 (1.5일)

- PGS 플러그인 붙이고 자동 로그인
- `/auth/pgs`, 서버 측 구글 확인
- 익명 계정 → PGS 계정으로 승격(기존 기록 그대로 물려받기)
- 갈라짐 선택 화면

→ **"폰 바꾸니 처음부터"** 가 풀린다. **유저 동작 없음.**

### 4단계 — 뒷문 (0.5일)

- 복구 코드, 웹용 구글 로그인
- 설정에 「계정」 항목 (연결 상태 / 복구 코드 / 마지막 동기화 시각)

합계 **3일** 정도.

---

## 8. 정해야 할 것

1. **PGS 플러그인** — Capacitor 용 플레이 게임즈 플러그인을 하나 골라야 한다.
   관리 상태와 PGS v2 지원 여부를 확인한 뒤 정한다. 마땅한 게 없으면 얇은
   네이티브 브릿지를 직접 쓴다(호출이 두 개뿐이라 부담이 크지 않다).

2. **Play Console 설정** — 플레이 게임즈 서비스 등록 + OAuth 웹 클라이언트 ID.
   한 번 하면 끝이지만 **3단계의 선행 조건**이다. 미리 해 두는 게 좋다.

3. **기존 유저 27명** — 업데이트 후 첫 실행에서 로컬 세이브가 서버로 올라간다.
   3단계에서 PGS 로 승격될 때 그 기록을 그대로 물려받는다. 잃는 사람 없음.

4. **세이브 보관 기간** — 지금 규모면 무제한이어도 SQLite 로 충분하다.

## 9. 한 줄

**유저는 아무것도 하지 않는다.** 앱을 켜면 플레이 게임즈가 조용히 신원을
확인하고, 세이브가 서버에 오간다. 폰을 바꿔도 그냥 이어진다.
설정에 있는 「계정」 항목은 안 봐도 되는 물건이다.
